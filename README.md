# 切片值班台（常规底图两名额分层调度 / 应急航片单进程插队）

FastAPI + Pillow 的切片演示服务：内置常规底图、应急航片各一张（2048×2048，启动时自动生成）。
常规底图按缩放层 z0→z3 切片，两个渲染名额、跨层预渲染「算完先持有、本层出齐才出图」；
应急任务受理即抢占，全程只运行一个渲染子进程。

## 快速开始

```bash
docker compose up --build
# 打开 http://localhost:8000
```

本地开发（Python 3.11+）：

```bash
pip install -r requirements.txt
DATA_DIR=./data TILE_DELAY=0.15 uvicorn app.main:app --host 0.0.0.0 --port 8000
```

环境变量：`DATA_DIR`（源图/瓦片/日志目录，默认容器内 `/data`）、`TILE_DELAY`（每张瓦片模拟渲染耗时秒数，默认 0.15，调大可放慢演示节奏）。

## 调度规则（需求逐条落地）

### 常规底图

- **两名额**：最多两个渲染 worker；「正在渲染」与「算完待出图（持有）」两类合计不超过 2 张。
- **分层推进**：同一缩放层内，瓦片算完立即原子发布 PNG 并更新进度。
- **跨层预渲染**：本层最后一张还在算、出现空位时，先派下一级的一张瓦片；它算完后**只持有不发布**，
  等本层全部出齐的瞬间才发布，然后才进入下一层（每个层边界各预渲染一张：z1/0/0、z2/0/0、z3/0/0）。
- **本层失败**：本层任一瓦片失败立即停止派发新瓦片；已在算的瓦片成功后照常发布；
  下一级的预渲染（在算或已持有）一律作废；在算瓦片清空后任务判失败。
- **预渲染延迟失败**：预渲染瓦片先失败时，本层照常收尾，直到本层出齐后才报告下一级的错误。
- **失败重试只补缺片**：已发布 PNG 留在磁盘，重试/续做时重建计划自动跳过，已发布瓦片不重算。

### 应急插队

- 受理应急时**中止常规全部 worker、舍弃所有未发布/持有瓦片**（staging 目录全清）；
- 应急全程**只运行一个渲染子进程**，常规完全停摆；
- 应急无论成功或失败，结束后常规自动续做，且**只算缺片**。

## 页面演示

1. **跨层出图**：点「启动切片」，观察每层最后一张在算时，下一级一张瓦片先变黄色「已算完·待出图」，
   本层出齐瞬间它才变绿发布，随后进入下一层。
2. **分层失败重试**：「指定失败瓦片」填 `2/0/0` 再启动——z2 失败停派、在算的照常发布，任务判失败；
   清空输入再点启动即只补缺失瓦片。填 `3/0/0` 可演示 z3 预渲染先失败、z2 照常出齐后才报错。
3. **应急插队**：渲染中点「启动应急切片（插队）」，常规未发布瓦片全部舍弃、应急单进程渲染；
   应急结束后常规自动续做只算缺片。勾选「模拟渲染失败」可演示应急发布 10 张后崩溃、常规仍续做。
4. 点击任意已发布瓦片可在新标签页打开对应 PNG；「重置」清空该任务已发布瓦片（任务空闲时才允许）。

## 实现内容

- **常驻 worker 池**（`app/worker.py`）：worker 为常驻子进程，stdin 行协议派单、stdout 行 JSON 上报。
  常规任务 2 个 worker（两名额）、应急 1 个。worker 只把成品写到调度器指定的 `.staging/<id>.png`，
  **发布（`os.replace` 原子改名）或作废（删除）全部由父进程调度器决定**，因此「持有/作废/延迟发布」
  只在调度器一侧实现。管道下 `TextIOWrapper` 行迭代是块缓冲的，worker 改用 `select + os.read(0)`
  自行按行解析，保证单行命令不滞留。
- **单协程串行状态机**（`app/scheduler.py`）：所有 worker 事件经 `asyncio.Queue` 汇总到一个调度协程，
  状态变更无需加锁；100ms 心跳 tick 驱动「持有等本层出齐」等无事件场景的再次派发与层收尾。
  派单只 `write` 不 `await drain`，背压在主循环每次迭代统一排空，避免主协程被管道阻塞。
- **中止双通道**：父进程写 `ABORT`（worker 的 `select` 立即唤醒，约定退出码 42）+ SIGTERM 双保险，
  不依赖信号即可在禁信号沙箱工作。
- **失败钩子**：常规 `?fail_tile=Z/X/Y`（指定瓦片崩溃，演示分层失败/延迟失败）；
  应急 `?simulate_fail=true`（发布 10 张后以退出码 3 崩溃）。
- **API**：
  - `GET /api/status` 两任务快照（状态、百分比、当前层、在渲/持有清单、分层状态、已发布清单）；
  - `POST /api/jobs/{kind}/start`（幂等；regular 支持 `fail_tile`，emergency 支持 `simulate_fail`）；
  - `POST /api/jobs/{kind}/reset`（任务进行中返回 409）；
  - `GET /tiles/{kind}/{z}/{x}/{y}.png`（未发布 404）、`GET /sources/{kind}.png`、`GET /api/meta`、`GET /`。
- **源图**（`app/sources.py`）：启动时用 Pillow 生成两张 2048×2048 测试图（渐变 + 网格 + 坐标标注），已存在不覆盖。

## 实测结果

环境：Python 3.11 / FastAPI + uvicorn 单进程 / Pillow，`TILE_DELAY=0.15`。
自测脚本 `scripts/selftest.py`（仅标准库），对准运行中的服务执行：

```
BASE=http://127.0.0.1:8000 DATA_DIR=./data python3 scripts/selftest.py
```

实测五项全部通过：

- **测试A 跨层出图与名额**：85/85 出齐；在算+待出图名额峰值=2（≤2）；日志确认 z0/z1/z2 三个层边界各发生一次
  「预渲染完成并持有 → 等本层出齐 → 发布持有瓦片」，持有瓦片与发布瓦片一致且持有早于发布；分层数量 1/4/16/64 正确；
  抽样瓦片为合法 PNG 可 HTTP 取；完成后 staging 无残留。
- **测试B 本层失败 + 重试**：`fail_tile=2/0/0` 时 z0/z1 完整出齐 5 张后 z2 失败停派、z3 零发布；
  清空钩子重试补齐至 85/85，原 5 张 mtime 未变（未重算）。另实测失败时同时在算的 `2/0/1` 成功后照常发布。
- **测试C 预渲染延迟失败**：`fail_tile=3/0/0` 时 z0/z1/z2 完整出齐 21 张、z3 零发布；日志确认 z3 预渲染先失败被登记，
  z2 在延迟窗口内照常发布出齐后，才上报任务失败。
- **测试D 应急插队**：常规发布 15 张后受理应急，0.06s 内应急接管、常规 `interrupted`、常规 worker 清零、
  未发布 staging 全舍弃；应急 85/85 且其 running 期间渲染进程峰值=1（单进程）；常规续做 85/85，旧 15 张全保留。
- **测试E 应急失败续做**：应急发布 10 张后失败，常规仍续做至 85/85，应急已发布瓦片仍为合法 PNG 可取。

接口核验：`/`、`/app.js`、`/style.css`、`/sources/{kind}.png` 均 200；已发布瓦片 200、未发布/越界 404；
非法 `fail_tile` 400；运行中 reset 409；重复 start 幂等 200。

## 未完成项 / 说明

- 本交付环境无 Docker 守护进程且沙箱禁止跨会话 `kill`，`docker compose up --build` 未在本机实际构建执行；
  Dockerfile / compose 为标准写法（已固定 uvicorn 单 worker），应用本体在容器外以相同命令实测通过，
  SIGTERM 通道因沙箱限制未能实测，stdin ABORT 通道（退出码 42）已实测有效。
- 外部 `SIGKILL` 模拟 worker 崩溃的 `_on_exit` 容错分支因沙箱禁 kill 未做端到端验证，逻辑经代码审查确认
  （无 error 事件退出时按瓦片类型分别走层失败/预渲染延迟失败）；带 error 事件的 worker 崩溃已由测试 B/C 覆盖。
- 调度状态在内存中，必须单 uvicorn worker 运行；服务重启后已发布瓦片保留，但未完成任务需重新启动（不自动续跑）。
- 渲染耗时用 `TILE_DELAY` 模拟，未接真实切图负载；瓦片方案为单源图 z0–z3 固定金字塔，未做 XYZ 坐标系对齐与多比例尺重投影。
- 未做鉴权与并发操作限流（重复启动幂等，重置仅做空态校验）。
